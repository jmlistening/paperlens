# PaperLens 小规模对照评测 v1

日期：2026-10-21。先固定题目、原文依据和程序，再收集真实模型输出。

## 这一步做什么

共 6 道题、3 篇已有原文，分别覆盖实验配置、构图信息边界、检索机制、表格数值、奖励层级和不可回答边界。RCER 已用于开发调试，不进入这组试评测。题目由项目开发者编写，是小规模诊断集，不是公开基准或统计意义上的独立大样本评测；后续若按本组结果调参，本组就成为开发集，正式验收应另留新题。

`questions.json` 只有问题和论文版本信息；`reference_criteria.json` / `REFERENCES.md` 给人工核对用。原文锚点已逐条核对 PDF，只合并空白，页码为 PDF 物理页。参考答案不会传给模型，也不要把 eval 目录加入检索语料。

## 安装和第一步

将更新包中 `paperlens_agent` 文件夹里的内容合并到现有 `<repo>`。确认 `<repo>\run_eval.py` 与 `app.py` 同级。新增脚本、测试和评测资料；更新项目笔记。不替换现有业务脚本、PDF、索引、模型缓存或配置。

在 Anaconda Prompt 中：

```bat
conda activate paperlens
cd /d <repo>
python run_eval.py --check
```

检查所有题目的 PDF 哈希、论文范围和索引一致性，不加载嵌入模型、不读取 `.env`、不调用模型 API。复用现有运行环境，无新增第三方依赖。若检查报错，先把完整终端输出发回来，不要直接重建索引。

检查通过后，先只跑第一题：

```bat
python run_eval.py --run --cases Q01
```

这条命令实际使用本机已有 API 配置，会消耗用量；最多 8 次模型请求，无自动重试。失败即停止后续任务。最多请求次数不等于人民币费用上限。不要同时在网页提问、更新论文库、改提示词或启动另一批评测；终端会显示每个阶段。

此次通过原有 CLI 执行：因此会像普通问答一样写入历史记录，并更新当前检索结果文件；旧检索结果由原固定流程归档。论文、索引、配置不会被评测脚本改写。

结束后终端给出 `eval\results\时间戳.zip`。把这个 ZIP 发回来，先核对第一题三个模式的回答和记录，再继续其余题目。无需截图所有中间日志，也不要上传 `.env`。导出包只收集本批记录、问题依据和根目录 Python 源码，不收集 `.env`、PDF、索引、模型缓存或以往问答。若自行把密钥写进 Python 源码，应先移回配置文件再运行。

后续已准备好的命令（第一题验收后再执行）：

```bat
python run_eval.py --run --cases Q02,Q03,Q04,Q05,Q06
```

这批最多 40 次请求。不要为得到更好答案反复挑结果；每次运行单独留档。没有自动续跑或重试功能，失败后先检查记录，再决定重跑哪个题目，重复整题会重新支付已经成功模式的调用费用。

## 对照设置

| 模式 | 原脚本 | 检索轮数上限 | 模型请求上限 | 最终证据上限 |
|---|---|---:|---:|---:|
| fixed | run_qa.py | 1 | 2（重排、回答） | 3 |
| agent_one | run_agent.py | 1 | 2（决策、回答） | 6 |
| agent_multi | run_agent.py | 3 | 4 | 6 |

保留原有提示词与检索逻辑。没有证据或重排筛空时，实际请求可能更少。fixed 与 Agent 的证据数量、选证据方法、回答提示词均有差异，所以差异不能全部归因于补检索。单轮与多轮 Agent 使用同一实现和最终证据上限，改变可用补检索预算，帮助观察迭代的作用；不预设多轮一定更好。语义检索与 BM25 是可选择的工具，没有分数融合。

模式顺序按题号轮换：Q01 fixed→agent_one→agent_multi；Q02 agent_one→agent_multi→fixed；Q03 agent_multi→fixed→agent_one，之后重复。每模式各一次，没有固定随机种子或修改模型默认 temperature；模型服务仍可能有随机性，单次结果不代表稳定均值。

## 冻结和可追溯性

每批记录全部根目录 Python 源码、评测资料、PDF、语料与向量索引的 SHA-256，以及 Python、依赖版本、平台信息。PDF 与索引只记录哈希，不复制到结果包。每个任务前后检查冻结文件，变化即停。不同批次比较前，人工比对 `input_sha256`；代码、数据或题目不同就不能混为同一轮实验。

沿用本地已配置模型及原参数；返回模型名保存在记录中，一批中出现不同名称会停止。不要在批次之间修改模型/服务配置。脚本不导出密钥或 API 地址；模型别名相同也不保证服务端权重永远不变，运行日期需保留。

Agent 请求、响应、轨迹、证据和答案完整归档。固定流程保留原候选、重排原始返回、回答原始返回及答案，提示词和构造请求的源码随包冻结。只归档本次新建目录，并核对问题及论文范围；无法唯一关联时停止，不使用“最新答案”猜测。

## 质量怎么评

用 `REFERENCES.md` 对照原文和每个模式的 `answer_result.json`，填写 `review_template.json` 的副本。先看中文要点，再看对应引文是否足够支持全部表述；不能只看有没有引用或 coverage 是否显示通过。

1. 每个评分要点：`covered`＝全部事实正确且完整；`partial`＝部分正确、仍有遗漏；`missing`＝未回答；`incorrect`＝事实、数字、单位、范围或逻辑错误。Q06 第二项是条件项，未补充实验范围则填 `not_applicable`。
2. 对每条中文回答要点：引文支持度记 `full / partial / unsupported`，附原句和解释。程序的原句匹配不等于语义支持。
3. 额外记录虚构内容、遗漏、错误拒答、输出失败。接口失败不应被静默删掉；单列成功数、失败数和未运行数。
4. Q06 重点是明确没有所求金额、不编造估算。可正确拒答，不强求某个 `status` 值。对可回答的 Q01～Q05，空答不能因“没有幻觉”而算通过。
5. 题级通过要求：适用的评分要点全部 covered、额外事实没有错误、所有事实性要点的引文支持充分；否则记录具体缺口，不把部分通过写成满分。

`answered / partial / insufficient` 和 coverage 均是模型自评，不作为评分答案。`human_quality` 初始为 null，不自动生成分数。先给逐题结果和计数，不从 6 题宣称通用准确率或显著提升。后续修复要另起版本并保留本轮结果。

## Token 与耗时

- fixed 的完整 Token 包含重排和回答；Agent 包含全部决策与回答。按原始返回累计，不重复统计复制到历史的相同答案。
- 缺失用量或超时不记成 0。`known_total_tokens` 仅为已返回的部分，`complete=false` 时不能拿来当总成本；旧固定流程失败时可能无法确定请求次数，明确写 null。
- 记录从启动原 CLI 到退出的端到端秒数，包括 Python 启动、模型加载、检索、API。固定流程有多个子进程，因此不是纯推理耗时或检索速度对比。未做冷缓存控制、GPU 同步基准或重复测量，不能凭一次秒数宣称性能提升。
- `SUMMARY.md` 方便查看；`manifest.json`、`tasks/*/metrics.json` 和原始记录用于复核。论文中自己的准确率/能效结果不是 PaperLens 的项目指标。
